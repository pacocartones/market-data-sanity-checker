# Market-data incidents

A shared list of real cases where market data was wrong in a way a checker should catch.
One row per case. Each row says what a checker should report **and what that check does not
establish**, so a passing check is never read as more than it is.

Started in [#35](https://github.com/pacocartones/market-data-sanity-checker/issues/35). PRs
welcome: add a row, link the evidence, and keep the last two columns honest.

## Columns

- **Case**: a short name.
- **Source**: the provider, feed or tool where it happened (`any` when it is not provider-specific).
- **What happened**: the defect, in one or two sentences.
- **Evidence**: a public link (issue, post, fixture). No private data.
- **A checker should report**: the finding, with the rule if mdsc has one.
- **The check does NOT establish**: what a pass of that check still leaves open.
- **Reported by**: who brought the case.

| Truncated tail passes a count-only comparison | any | A subject series ends two sessions before the authority. A comparison of session counts with a tolerance (10% in the original probe) passed with 2 of 21 sessions silently deleted. With equal counts but an entirely different window, a count comparison also passes. | [#35](https://github.com/pacocartones/market-data-sanity-checker/issues/35), [`wrong_window.py`](https://github.com/arian-gogani/nobulex-registry/blob/main/examples/wrong_window.py) | `SERIES_TAIL_TRUNCATED` naming the authority dates absent from the subject; with no shared session, `INSUFFICIENT_OVERLAP` (critical), never a truncation | That the shared sessions are correct: prices, adjustments and volumes need their own rules | @arian-gogani |
| Free endpoint serves unadjusted data after adjusted endpoint becomes paid | Alpha Vantage | The Python client reports that `TIME_SERIES_DAILY_ADJUSTED` is unavailable to free accounts. Its free `TIME_SERIES_DAILY` response is valid OHLCV, but has no adjusted close, dividends or splits. The connector documents this distinction at the pinned source revision. | [alpha_vantage#349](https://github.com/RomelTorres/alpha_vantage/issues/349), [`alphavantage.ts` at the reviewed revision](https://github.com/pacocartones/market-data-sanity-checker/blob/86ffa3af564704c0d5ec6ca7ae16c45c9b810a82/src/connectors/alphavantage.ts#L17-L20) | Report which endpoint or product tier was requested and served, and mark adjustment and corporate-action coverage unavailable when the requested adjusted endpoint was not served. The parser alone cannot infer a product downgrade from empty action lists. | That the raw prices are wrong. They may be correct unadjusted prices, and a missing action list by itself does not prove the symbol had an action. | @pacocartones, @arian-gogani |
| Adjustment default changes across client versions | yfinance | In yfinance 0.2.51, `download()` changed the default for `auto_adjust` to `True`. Users comparing output across versions reported changes to adjusted-close behavior and output columns. The project later merged a warning for callers that omit the argument. | [yfinance#2230](https://github.com/ranaroussi/yfinance/pull/2230), [#2214](https://github.com/ranaroussi/yfinance/issues/2214), [#2219](https://github.com/ranaroussi/yfinance/issues/2219), [#2198](https://github.com/ranaroussi/yfinance/issues/2198) | When a caller has a prior snapshot, report a changed adjustment basis or output schema for the same symbol and requested window across client versions. `CLOSE_DIVERGENCE` compares two sources, so it does not cover a same-provider version change. | Which basis the caller intended. The default change was deliberate; a detected difference does not establish that either series is corrupted or that the adjusted arithmetic is wrong. | @arian-gogani |
| Phantom price drop without corporate action | Yahoo Finance via yfinance | For RAYMOND.NS on 2025-05-14, the daily close dropped from 1564.30 to 551.20 without any split, bonus or demerger registered on the exchange. | [yfinance#2519](https://github.com/ranaroussi/yfinance/issues/2519) | `RETURN_SPIKE` flags the -64.8% single-day drop because it easily exceeds the default economic gate (4%) and full severity cap (8% or z-score >= 5). `SPLIT_NOT_ADJUSTED` does not apply because the ratio 1564.30 / 551.20 (~2.84) does not match any common integer split ratio. | That the new price is objectively wrong and the prior price was right; a spike check only flags that the move is an unexplained statistical outlier. Validating the true market close requires cross-checking external venue feeds such as NSE or TradingView. | @sahilpurav |
| NaN OHLC prices with positive volume on completed session | Yahoo via yfinance | yf.download('ATR.WA') for a completed session (2026-07-09) returned all four OHLC prices as NaN with volume 6527; valid prices were backfilled by Yahoo later after the market opened. | [yfinance#2895](https://github.com/ranaroussi/yfinance/issues/2895), [#2925](https://github.com/ranaroussi/yfinance/issues/2925) | If in-memory bars pass JS NaN values, `PRICE_NONPOSITIVE` flags all four fields because `Number.isFinite(NaN)` is false (`src/rules/price/price-nonpositive.ts:31`). However, through standard file ingestion paths, the bar fails schema validation before rules run: JSON `null` (representing NaN) is rejected by `barSchema`'s `z.number()` (`src/schema/market-data.ts:26-29`), and CSV empty cells are omitted by `parseOhlcvCsv` (`src/ingest/csv.ts:101-103`), failing required number schema checks. | That the session was actually traded or that the volume figure is accurate; conversely, non-finite or missing prices on a recently completed bar do not prove permanent data corruption, as upstream feeds like Yahoo may asynchronously backfill missing OHLC fields after market open. | @adrianwojcik |
| Zero-volume 4-hour bars coming from the upstream feed | Yahoo via yfinance | `yf.download(tickers='BTC-USD', period='1y', interval='4h')` returned `Volume` 0 in about half of the rows, with no pattern the reporter could identify, and the Yahoo Finance site did not let them check intraday intervals. Another user traced it to Yahoo's raw `/v8/finance/chart/BTC-USD` JSON, whose `volume` array carries explicit `0` and `null` entries at those timestamps. yfinance closed the issue as `not_planned` and referred to its price-repair documentation. | [yfinance#2686](https://github.com/ranaroussi/yfinance/issues/2686), [price repair notes](https://ranaroussi.github.io/yfinance/advanced/price_repair.html) | Out of scope for MDSC, and the row should say so: the unit of analysis is the daily bar, intraday streams are not read (`README.md`, "When NOT to use it"). The daily equivalent is `ZERO_VOLUME_MOVED` (warning), which flags a bar with `volume === 0` and `high != low` (`src/rules/price/zero-volume-moved.ts:31-33`) and stays silent when `high == low`, because flat prices with zero volume are not a contradiction. Aggregation also hides the case above: at daily resolution the session is one bar, and unless that daily bar itself reports zero volume while its high differs from its low, zeros inside the day never reach the rule. | Whether a zero-volume bar is genuine inactivity, a halt or an upstream omission; the rule's own comment cites 1COV.DE as a documented corrupt vendor row and tells the user to verify against the source. Diagnosing the intraday case needs the feed at 4-hour resolution, which MDSC does not ingest. | @krydazo |
| Repair step invents a split from a volatility jump | Yahoo via yfinance | `yf.download('GME', period='max', repair=True)` flagged every row up to 2021-01-26 as `Repaired? True` (2021-01-26 close 147.98) and rows from 2021-01-27 as `False` (close 86.8775): the maintainer explains the repair took the jump on 2021-01-27 to mean Yahoo had not applied the 2022-07-22 stock split, so it scaled all earlier data by 4. A second report says NVDA before 2004-08-06 was scaled the same way, a real fall of about 3:2 taken for a split. The maintainer points to PR #2668 as the fix. | [yfinance#2660](https://github.com/ranaroussi/yfinance/issues/2660), [PR #2668](https://github.com/ranaroussi/yfinance/pull/2668) | In single-source checking, `SPLIT_NOT_ADJUSTED` does not fire at the repair boundary (2021-01-26 to 2021-01-27): `matchSplitRatio` finds no common ratio for the −41.3% one-day move inside the 5% tolerance, so the rule moves on (`src/rules/price/split-not-adjusted.ts:58-59`). `RETURN_SPIKE` does fire and keeps its warning: the median and MAD of returns are computed once over the whole series (`buildDataProfile`, `src/rules/engine.ts:16-22`), so on a long history of ordinary daily moves a −41.3% return passes the 4% economic gate and the modified z-score gate at 3.5 — the z gate would only fail if the series' return MAD exceeded about 8% (0.6745 × 0.413 / 3.5) — and a move of at least 8% keeps full severity instead of dropping to `info` (`src/rules/price/return-spike.ts:84-97`). Comparing against the unrepaired series is what marks the boundary as artificial: `mdsc compare` emits **one** `CLOSE_DIVERGENCE` finding once the median daily divergence over shared dates exceeds 0.5%, and names only the worst date in `where` (`src/compare/rules/close-divergence.ts:47-56`) — the scaled years are not reported session by session. | That a repaired series passing the single-source rules is clean, nor that a flagged boundary is a defect: `RETURN_SPIKE` only says the day is statistically unexplained, and GME's genuine January-2021 moves raise the same warning. `CLOSE_DIVERGENCE` says two feeds disagree systematically and points at the worst date — not at the date range the repair touched, and not at which feed is right. Proving over-repair needs the corporate-action calendar (Yahoo logged the 2022-07-22 split) plus the raw stream or an independent venue. | @theXYZT |
| Duplicate daily timestamp with differing volume | Yahoo via yfinance | The Yahoo chart API returned two daily rows for the same date with different volume values. yfinance users reported the duplicate for both `period='1d'` and explicit date ranges. | [yfinance#573](https://github.com/ranaroussi/yfinance/issues/573) | `TS_DUPLICATED` fires when two or more bars share a timestamp. Since these rows have different volume values, the rule cannot determine which bar is final. | Which row is correct or which volume is accurate. Dropping the last row alone does not establish a correct repair. | @pratik-choudhari |
| Temporary multi-symbol loss of split adjustment in adjusted close | Yahoo via yfinance | From Friday 2021-12-10, adjusted close for the symbols the reporter named as Apple, Nvidia and Tesla (start date 2018-01-01) "no longer reflect the stock splits", and the charts showed a steep decline on each split date; a commenter added that "the price is no longer adjusted to splits, and split info is missing". The reporter later confirmed that "the adjusted price issue has been fixed as of 12.14.2021", so the report covers a temporary window, 2021-12-10 to 2021-12-14, and the issue was closed as not planned in October 2022. | [yfinance#906](https://github.com/ranaroussi/yfinance/issues/906) | Read the precondition first: `SPLIT_NOT_ADJUSTED` works on `close` only (`src/rules/price/split-not-adjusted.ts:55-58`), and the Yahoo connector stores adjusted close as a ratio, `bar.adjustmentFactor = adjclose / close` (`src/connectors/yahoo.ts:127-128`), which the rule never reads. So the incident is visible to the rule only when the adjusted series was ingested as `close` — a file whose close column carries adjusted values, or a snapshot taken that way. With that satisfied and no split metadata on the series, the rule matches the one-session drop against common split ratios (`matchSplitRatio`, line 58), finds no registered split inside the window (lines 62-66) and blocks. When the split list is present but the prices were never adjusted, `explained` is true and the rule stays silent; the report describes the other shape, split info missing along with the adjustment, which is the one the rule catches. | That the vendor's own fix reached the consumer: a database snapshot ingested during 2021-12-10 to 2021-12-14 keeps the broken split history after Yahoo corrects its side, and the rule's silence is equally consistent with an intact-but-unadjusted feed. Re-fetching the window and running `mdsc compare` against an independent provider is what turns "no finding" into evidence. | @bruce1095 |
