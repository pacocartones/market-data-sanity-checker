# Market-data incidents

A shared list of real cases where market data was wrong in a way a checker should catch.
One file per case in [`incidents/`](incidents/); the table below is generated from those files. Each case says what a checker should report **and what that check does not
establish**, so a passing check is never read as more than it is.

Started in [#35](https://github.com/pacocartones/market-data-sanity-checker/issues/35). PRs
welcome: add **one file** to `incidents/` (see the template below), link the evidence, and keep the last two sections honest. **Do not edit this file's table**: it is generated, and it is the only way two cases never touch the same line.

## What a case file says (the table columns)

- **Case**: a short name.
- **Source**: the provider, feed or tool where it happened (`any` when it is not provider-specific).
- **What happened**: the defect, in one or two sentences.
- **Evidence**: a public link (issue, post, fixture). No private data.
- **A checker should report**: the finding, with the rule if mdsc has one.
- **The check does NOT establish**: what a pass of that check still leaves open.
- **Reported by**: who brought the case.

## Before you open a pull request: a checklist for a case

Cases are reviewed against their sources, so the same few problems cost the most review time. Check these first:

1. **Every fact is in the cited source.** Numbers, dates, tickers, versions and the reporter come from the issue or post itself, not from memory. If the source does not give a ratio, a date or a cause, say so; do not fill it in. Quote the sentence you rely on in the pull request.
2. **Reported by** is the handle of the person who opened the issue (check it), not the maintainer who answered.
3. **What a rule does** is read from the rule's code, not inferred from its name: open the rule, check which fields it reads, its default parameters, and whether the data would reach it through the connector or through file ingest (for example, the Yahoo connector keeps adjusted close as a ratio and leaves OHLC raw).
4. **Scope.** mdsc works on daily bars. If the case is weekly, monthly or intraday, say at the start of the row that it is outside that unit and what, if anything, a comparison against another source can still show.
5. **Say what you ran and what you only read.** "No rule fires" must say whether you ran it or read the rules.
6. **Line references** point to the code that decides the behaviour (the `check()` body), not to a doc comment.
7. **One case per pull request, one new file.** Name it with lowercase words joined by hyphens (`incidents/vwilx-capital-gains-in-dividend.md`) and copy the front matter and the four sections from any existing file. Do not touch `incidents.md`: the maintainers regenerate its table (`pnpm incidents:index`) at release time. `pnpm incidents:check` tells you whether your file is well formed.
